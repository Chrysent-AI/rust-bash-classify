# Porting notes

This repository is a structural Rust port of the Python `bash-classify` project. The port favors side-by-side review and behavioral parity over idiomatic rewrites: when observed Python behavior at the recorded source commit disagrees with prose documentation, observed behavior is the oracle.

## Source of truth

- Python source repository: `/home/chrysent/devel/bash-classify`
- Recorded source commit: `8553440aa4d935dd14a8cbb15338ecac92100720`
- Vendored files: `vendor/commands/*.yaml`, `vendor/schemas/command.schema.json`, and `vendor/SPEC.md`
- Sync metadata: `VENDOR.json`

Vendored files are copied byte-for-byte and are not edited in this repository. Run `scripts/vendor.sh --check` to verify that the committed vendor tree and generated embed table still match the recorded Python commit. If the Python source of truth changes behavior, sync the vendor files, regenerate the golden corpus with `scripts/harvest_goldens.py`, then review the resulting expected-output diff.

## Module map

| Rust module/file | Python counterpart | Notes |
|---|---|---|
| `src/models.rs` | `src/bash_classify/models.py` | Ports the dataclasses/enums for classifications, risks, command definitions, invocations, redirects, and result objects. Rust enums keep the same wire strings and severity ordering. |
| `src/parser.rs` | `src/bash_classify/parser.py` | Ports tree-sitter Bash command extraction, redirect extraction, context tracking, background detection, and parse-warning behavior. |
| `src/matcher.rs` | `src/bash_classify/matcher.py` | Ports command lookup, option/subcommand matching, strict handling, delegation modes, alias resolution, and result assembly. |
| `src/classifier.rs` | `src/bash_classify/classifier.py` | Ports expression aggregation, redirect/system-path risk elevation, special builtins, directory/read/write path collection, and parse-warning fallback classification. |
| `src/database.rs` | `src/bash_classify/database.py` | Ports lazy command loading, user override shadowing, YAML parsing into command definitions, schema-shaped field handling, and default user config discovery. |
| `src/cli.rs` | `src/bash_classify/cli.py` | Ports stdin handling, exit-code mapping, help/version handling, fixed-order JSON serialization, conditional field omission, and Python-style ASCII JSON escaping. |
| `src/bin/rust-bash-classify.rs` | Python console-script entry point | Thin binary wrapper around `bash_classify::cli::run()`. |
| `src/commands_data.rs` | Python package `commands/` directory | Generated by `scripts/gen_commands_data.sh`; embeds the vendored YAML files into the Rust binary with `include_str!`. This has no Python module counterpart but preserves the same built-in command database content. |

Helper code lives next to the Python module it mirrors. For example, path elevation helpers live in `classifier.rs`, serialization helpers live in `cli.rs`, YAML field parsing helpers live in `database.rs`, and delegation/option-tokenization helpers live in `matcher.rs`.

## Intentional Rust seams

- `CommandLookup` in `matcher.rs` captures the lookup operations that Python gets from dictionary-like database access. `CommandDatabase` implements the trait, and tests can use the same matching seam without changing matching behavior.
- Alias resolution is consolidated in one `resolve_alias_def` implementation used by both `matcher.rs` and `database.rs`. This avoids two copies of the same Python parity error-text logic.
- `ParseError` carries the parser's recursion-bound failure. The Rust walker uses `MAX_WALK_DEPTH = 256` as a practical guard against pathological nesting; Python relies on the interpreter recursion limit. Both produce the same class of parse warning: maximum recursion depth exceeded.
- `ClassifyError`, `MatchError`, and `DbError` are small Rust error types whose `Display` text is intentionally kept close to Python exception messages, because CLI exit-2 stderr includes those messages.

## Documented deviations

These deviations are implementation-language or product-name differences, not behavior improvements.

1. **Result-returning library signatures.** Python functions such as `match_command`, `classify_expression`, `load_database`, and `parse_expression` raise exceptions or return tuples directly. Rust returns `Result` at fallible seams and maps those errors to the same CLI behavior where applicable.
2. **Stdin readiness implementation.** Python uses `select.select` before reading stdin. Rust uses a reader thread and a first-readiness timeout before collecting the rest of stdin. The observable contract is preserved: empty input exits 1 silently, no initial stdin data exits 1 with the timeout message, and data that starts before the timeout may continue until EOF.
3. **Program name in user-facing strings.** The Rust binary is named `rust-bash-classify`, so help text, version text, timeout text, and internal-error prefixes use `rust-bash-classify` instead of Python's `bash-classify`.
4. **Version scheme remains independent.** Python at the recorded source commit prints `bash-classify 0.9.1`; this Rust crate currently prints `rust-bash-classify 0.1.0`. The long-term versioning/distribution decision is intentionally unresolved.
5. **UTF-8 decode errors are stderr-only error-path differences.** Invalid stdin bytes are rejected before classification and reported through the Rust CLI's error path; they do not affect successful JSON output parity.
6. **Empty-input wording follows observed Python behavior.** `vendor/SPEC.md` describes exit code 1 as a parse-error row, but Python actually exits 1 silently for stripped-empty stdin. Rust follows the observed behavior.
7. **Recursion threshold approximation.** Rust's `MAX_WALK_DEPTH = 256` is not Python's exact recursion limit. It is a bounded approximation that preserves the observable failure class for extreme nesting.
8. **YAML parser implementation.** Rust uses `serde_yaml`; Python uses PyYAML. No YAML 1.1 semantic discrepancy was encountered in the vendored command corpus or ported tests. If a future vendor sync exposes one, observed Python behavior remains the oracle and the discrepancy should be added to `PARITY.md`.
9. **Lazy loading retained.** The Rust database intentionally keeps Python's lazy parse-on-lookup behavior. Invalid YAML in an unrelated command file does not poison classification until that command is accessed.

## Golden corpus and differential policy

The golden corpus under `tests/golden/cases/` contains CLI inputs and expected Python outputs generated by `scripts/harvest_goldens.py`. `tests/golden_replay.rs` replays those cases through the Rust binary and requires byte-identical stdout and matching exit codes. Golden outputs are script-owned fixtures; do not hand-edit them to make a failing replay pass.

A live differential harness that runs Python as an oracle against newly generated inputs is intentionally deferred. The current golden infrastructure is the base for adding that later.

## Vendor policy

The Python repository remains the owner of command YAML, JSON schema, and the product specification. To sync:

1. Update `VENDOR.json` and vendored files with `scripts/vendor.sh`.
2. Regenerate `src/commands_data.rs` with `scripts/gen_commands_data.sh`.
3. If behavior changed, regenerate `tests/golden/` with `scripts/harvest_goldens.py` from the same Python commit.
4. Run `scripts/vendor.sh --check`, `scripts/harvest_goldens.py --check`, and the Rust test suite before committing.

The tree-sitter Bash grammar version is pinned in `Cargo.lock` and recorded in `VENDOR.json`; vendor checks fail if the Python lockfile drifts from the pinned Rust grammar version.
